# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Website for a self-defense/personal protection company. The end goal is a chatbot agent that recommends a martial art from user input; the current state is the marketing/catalog foundation (landing page, martial arts index, martial art show page) running on **mock data**. Planned stack: Next.js + Supabase (Supabase not wired up yet).
The real per-art details (fields and content) have not been provided. Ask the user for them art by art when that step comes; the current fields are placeholders.

## Commands

```bash
npm run dev     # dev server at http://localhost:3000
npm run build   # production build; also type-checks and prerenders all routes
npm run lint    # eslint
```

There is no test runner configured. `npm run build` is the main correctness check (it fails on type errors and prerender errors).

## Next.js version caveat

This is Next.js 16 with React 19 — newer than most training data. `AGENTS.md` instructs reading the relevant guide in `node_modules/next/dist/docs/` before writing Next code. Things already confirmed here:

- **Cache Components is enabled.** Non-deterministic values such as `new Date()` or `Math.random()` in server components fail prerendering ("unstable value ... while prerendering"). Use `"use cache"`, a client component, or `await connection()` instead.
- Route props use the globally-available typed helpers `PageProps<"/route/[param]">` and `LayoutProps<"/">` (generated by `next dev`/`next build`/`next typegen`, no import), and `params` must be awaited.

## Architecture

- App Router under `src/app`, import alias `@/*` → `src/*`. All pages are server components.
- **Data-access seam:** pages never import mock data directly. They call the async functions in `src/lib/martial-arts.ts` (`getMartialArts`, `getMartialArtBySlug`), which currently read from `src/lib/mock-data/martial-arts.ts`. The Supabase migration should only change the bodies of those functions (and `src/lib/types.ts` if the schema changes), not the pages. Landing-page copy (mission, benefits, services, `siteName`) lives in `src/lib/mock-data/site-content.ts` and is imported directly.
- `src/app/martial-arts/[slug]/page.tsx` uses `generateStaticParams` over `getMartialArts()` and `notFound()` for unknown slugs; `src/app/not-found.tsx` is the 404.
- **Styling:** themed after HBO's "Warrior" (1870s San Francisco Chinatown) — dark and light themes. Colors are semantic CSS variables at the top of `src/app/globals.css` (`--bg`, `--surface`, `--line`, `--text`, `--text-dim`, `--red`, `--red-bright`, `--gold`, `--gold-dim`, `--on-red` for text on red): `:root` is dark (also the no-JS default) and `:root[data-theme="light"]` overrides it, so never hard-code a color — add a token with a value in both blocks. `data-theme` is set before first paint by a plain inline `<script>` in `layout.tsx`'s `<head>` (saved choice in `localStorage` → else OS preference → else dark) and flipped by `src/components/theme-toggle.tsx`, which has no React state; CSS picks which label shows. Don't swap that script for `next/script`: it queues the script into Next's runtime instead of running it during parsing, so light-mode visitors would see a flash of dark. React logs a dev-only "Encountered a script tag" warning for it; production is unaffected. Styling is plain hand-written CSS in that one file (Tailwind is installed but unused); markup stays semantic HTML with a few class hooks (`.card-grid`, `.card`, `.button`, `.facts`, …). Three fonts are loaded via `next/font/google` in `src/app/layout.tsx` and exposed as `--font-display` (Alfa Slab One, headings), `--font-body` (Crimson Pro), `--font-label` (Oswald, nav/labels). Keep new UI on those tokens.
- `.claude/launch.json` defines the `dev` preview server used by the desktop app's browser pane.

## Chatbot

A floating "Ask the Dojo" widget (`src/components/chat-widget.tsx`, mounted in `src/app/layout.tsx`) talks to `POST /api/chat` (`src/app/api/chat/route.ts`), which streams plain text from Claude Haiku (`claude-haiku-5-5`, override with `CHAT_MODEL`) via `@anthropic-ai/sdk`.

- **Key:** `ANTHROPIC_API_KEY` in the git-ignored `.env` (see `.env.example`). Without it the route returns a friendly 503 that includes the support phone.
- **Knowledge:** no retrieval. `src/lib/chat/knowledge.ts` reads every `content/martial-arts/*.txt` (file name = slug) into the system prompt built by `src/lib/chat/system-prompt.ts`, sent with `cache_control`. Adding or editing a write-up in `content/` changes the chatbot automatically; keep file names equal to the slugs in the mock data so `/martial-arts/<slug>` links resolve.
- **Behavior rules live in the system prompt only:** stay on martial arts/self-defense (decline everything else), answer only from the documents, recommend 1–2 arts after at most 1–2 clarifying questions, and escalate to the fictional rep (`supportRep`/`supportPhone`/`supportHours` in `src/lib/mock-data/site-content.ts`) when unsure. Re-check these with the manual scenarios (on-topic, recommendation, off-topic, escalation, injection) after any prompt change; there is no automated test.
- **Guards:** message/history length caps and a best-effort in-memory per-IP rate limit (`src/lib/chat/config.ts`). Haiku 5.5 rejects non-default `temperature`/`top_p`; the route sends `output_config.effort: "low"` and `thinking: { type: "disabled" }`. Keep thinking off: adaptive thinking draws on `max_tokens`, and a longer prompt made it use the whole budget, giving empty or cut-off replies. The route also writes a fallback message if a stream produces no text.
- **Tone:** the prompt asks for a joke in the opening/closing line of ordinary answers, and no humor (stated silently, never announced) on injury, health, violence, fear, or escalation hand-offs. After editing the tone, re-run the medical ("torn ACL") and vulnerable ("I was attacked") scenarios to confirm they stay joke-free.
- **Hard questions go to Sonnet, capped at 10/day site-wide.** Every request starts on Haiku with an extra `DIFFICULTY_CHECK` system block (`src/lib/chat/system-prompt.ts`) telling it to reply with exactly `ESCALATE_MARKER` (`config.ts`) for a genuinely hard question. `route.ts` holds back the first few characters, swallows the marker (visitors never see it), calls `claimSonnetSlot()` (`src/lib/chat/sonnet-budget.ts`), and if it returns true re-runs the question on `HARD_QUESTION_MODEL` (`claude-sonnet-5-5`, thinking on, effort medium, 4096 max tokens). If the budget is spent, Supabase is unconfigured or erroring, or Sonnet fails, Haiku answers instead (fails closed, so an outage can't overspend). The counter is the `claim_sonnet_slot()` SQL function over `chat_sonnet_usage` (`supabase/migrations/20261014000000_sonnet_daily_budget.sql`): a single atomic upsert, "today" in Pacific time, and **the limit (10) lives only in that function**; change it with a new migration. The table has no client grants. Anyone holding the public anon key can call the function and burn the day's slots, which only forces Haiku answers. A visitor message containing the marker text skips routing entirely (no routing block, no marker detection), so typing it cannot make Haiku trigger an escalation and spend a slot. Both models share the cached main prompt block; the routing block is uncached and Haiku-only. Check `npm run dev`/`start` logs (`chat: hard question answered by ...`) to see which model answered.
- If `next dev` serves stale CSS (another dev server already holding port 3000), use the `prod` preview config (`npm run build` first).

## Accounts and class booking

Supabase Auth (email + password, **no email confirmation**) plus a weekly class timetable that members reserve week by week. Everything degrades gracefully when `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` are unset (see `isSupabaseConfigured()` in `src/lib/auth.ts`): the public site works, `/login` and `/signup` say accounts are unavailable, the art pages say booking opens soon, and `src/proxy.ts` is a no-op. CI therefore needs no Supabase secrets.

- **Schema:** `supabase/migrations/*.sql` (+ `supabase/seed.sql`, fictional timetable). Tables `profiles` (auto-created by a trigger on `auth.users`), `class_templates` (one row per weekly slot; `art_slug` is a plain text slug, no FK, because arts are still mock data) and `bookings`. **Bookings are written only through the `book_class()` / `cancel_booking()` SQL functions** (clients have no INSERT/UPDATE/DELETE), which enforce capacity (row-locked), weekday, 4-week window, no overlaps, 10 upcoming per user, and a 2 h cancellation cutoff. Reads go through `get_schedule()`, `get_my_bookings()`, `get_roster()`. They return short error codes (`class_full`, ...) that `src/lib/bookings.ts` maps to messages, so keep the two in sync. Class times are stored as wall-clock + `timezone` (default `America/Los_Angeles`) and always displayed in that zone (`src/lib/format.ts`).
- **Roles:** `member` / `instructor` / `admin` in `profiles.role`. Members can only change their own name and phone (column-level grant); promote someone with SQL: `update profiles set role = 'admin' where id = '<uuid>';`. Admins manage `/admin` (add/deactivate weekly classes); instructors and admins see rosters at `/admin/roster/[templateId]`.
- **Code layout:** `src/lib/supabase/server.ts` (cookie client), `src/proxy.ts` (session refresh + optimistic redirect for `/account`, `/admin`; not the security boundary), `src/lib/auth.ts` (`getCurrentUser`, `requireUser`, `requireRole`, `safeNextPath`), data seam in `src/lib/classes.ts` and `src/lib/bookings.ts`, Server Actions in `src/lib/actions/{auth,booking,admin}.ts`. Pages never call Supabase directly. Authorization is re-checked in every action and enforced again by RLS.
- **Cache Components:** anything reading the session sits behind `<Suspense>` (header `AuthNav`, the art page's `ClassSchedule`, the body of `/account`, `/admin`, `/login`, `/signup`), so the art pages stay statically prerendered. Don't call `Date.now()`/`new Date()` inside a component (lint `react-hooks/purity`); put clock reads in lib functions such as `splitBookings` and `nextOccurrence`.
- **Setup for a new Supabase project:** put the URL and anon key in `.env`; in Authentication > Sign In / Providers > Email turn **off** "Confirm email"; run the migration (`supabase db push` or paste into the SQL editor) and optionally `seed.sql`. With confirmation off, unverified emails and bot signups are possible; `book_class` caps bookings per user as a cheap limit. Password reset is not built (needs email).
- **No automated tests for the app.** The SQL was exercised against an in-memory Postgres (PGlite) with stubbed `auth` objects: rules, RLS, grants. Re-do that, or test on a real project, after changing the migration. The test stub must NOT grant table privileges by default: newer Supabase projects don't auto-grant new tables to `anon`/`authenticated`, so the migration grants explicitly (a missing `GRANT SELECT` shows up as "permission denied for table" and makes every login look logged-out; `getCurrentUser` logs that case). Concurrency was tested against a real multi-connection Postgres (embedded build, 20-40 simultaneous `book_class` calls on 1-10 seat classes: never oversold; the same test with the `FOR UPDATE` removed booked 20 people into a 1-seat class, so the lock is what prevents it). Keep that lock if you edit `book_class`.
